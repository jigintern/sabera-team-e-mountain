# 峰ミル — SABERA に山の稜線と山名を重ねるアプリ

## Context

`sabera-team-e` の**星しるべ**は、SABERA スマートグラスに星座を重ねる Android アプリ。その**山版**を作る。SABERA に山の稜線を描き、山の名前を出す。

`/Users/kaito/Documents/jigintern/sabera-team-e-mountain` は**空のディレクトリ**で、git リポジトリですらない。ゼロから始める。

星しるべから引き継ぐ価値は、コードそのものより**実機で測って直した資産**にある。特に:

- **ヨードリフト補正** — グラスには磁力計が無く、ヨーは静止中も 44°/分 流れる。`YawDriftCorrector` が 0.0°/分 まで潰してある。再現には実機と何日もかかる
- **投影パイプライン** — `sky/Coordinates.kt`（約250行）に全ての符号規約が閉じ込めてある。ENU・北0°東回り・右手系・ステレオ投影 `r = 2tan(θ/2)`
- **グラス出力の予算計算** — RLE 圧縮サイズを送信前に自前で数えて溢れを防ぐ仕組み

一方で、**星と山は座標系以外ほぼ何も共有しない**。星は無限遠で時間とともに動き、互いを隠さない。山は有限距離で不動、そして**互いを隠す**。この差が設計の大半を決めた。

### 描画形式（#18）がなぜ「太く明るい線」なのか

グラスは**緑8階調・黒は透明**の波導ディスプレイ。ここに罠が両側にある。

- **塗りつぶしは本物の山を隠す** — 透明でない画素は実景に重なる。シナリオ#1では実物が目の前にある
- **細線は屋外で見えない** — 実測済み: 「暗い画素は屋外の空に負ける。2〜4px の点は背後の星と見分けが付かない」

星しるべが #46/#61 の実機フィードバック「矢印が非常に分かりにくい」で辿り着いた処方が答え: **最上段の階調(255)だけを使い、線幅を稼ぐ**。

なお RLE（連長32上限）のため**塗りつぶしのコストは黒背景とほぼ同じ**で、予算は制約にならない。制約は視認性のほうだった。

### 同梱方式（#5）に至った経緯

当初は「オンラインで都度取得」と決めたが、**実測して覆した**。海タイルは404で存在せず、再エンコードで大幅に縮むため、全国分の同梱が現実的だった（次節）。結果として**オフライン原則が全国で復活**し、オンラインは近距離を高精細化する**任意の上乗せ**になった。

## DEM の実測値（すべて自分で計測した数字）

### 配信形式のサイズ（鯖江周辺の実タイル）

| 形式 | サイズ/タイル |
|---|---|
| `dem_png`（PNG） | 110〜143 KB |
| `dem`（txt） | 409〜470 KB（gzip して 149〜192 KB） |

配信データは**1cm 分解能**で、下位ビットはこの用途では純粋なノイズ。**自前で int16 化＋行差分＋zlib** すると縮む:

| 量子化 | サイズ/タイル | 妥当性 |
|---|---|---|
| 1 m | 62.9 KB | 過剰 |
| 2 m | 52.8 KB | 5km先で0.35画素 — 近距離用に十分 |
| 4 m | 43.5 KB | 30km先で0.15画素 — 中距離用に十分 |
| 8 m | 34.2 KB | 80km先で0.09画素 — 遠距離用に十分 |

（グラスの1画素 = 0.066° = 35°÷528px）

### 全国分の同梱サイズ（標本抽出による実測）

**海タイルは 404 で存在しない**ため、日本を囲む箱のうち実在するのは 14〜23% だけ。

| ズーム | 画素 | 量子化 | 箱内 | 実在率 | 実在枚数 | 平均 | **全国合計** |
|---|---|---|---|---|---|---|---|
| z9 | 247 m | 8 m | 672 | 23% | 約156 | 26.7 KB | 4.1 MB |
| **z10** | **124 m** | **4 m** | 2,640 | 22% | **約581** | **32.1 KB** | **18.2 MB** |
| z11 | 62 m | 2 m | 10,355 | 14% | 約1,450 | 46.6 KB | 65.9 MB |

**検算**: z11 の 1,450 枚は、日本の陸地面積 378,000 km² ÷ z11 タイル面積 250 km² = 1,512 枚とほぼ一致する。標本抽出は信用してよい。

### なぜ z10 か（z9 では足りない理由）

z9 の 247m は**近距離で効かず、それが #3 の厳密オクルージョンを直撃する**。

| 距離 | z9(247m) | z10(124m) |
|---|---|---|
| 10 km | 21 画素 | 10.7 画素 |
| 20 km | 10.7 画素 | 5.3 画素 |
| 50 km | 4.3 画素 | 2.1 画素 |

鯖江から日野山は**9.6km**（実測。仰角4.41°で白山の2.40°より高く見える）。手前の山の形が 21 画素刻みでしか分からないと、その裏の白山が隠れているかの判定が外れる。**「隠れた山を描かない」と決めた以上、判定を外すのが最悪の振る舞い。**

## 中核アルゴリズム（新規部分）

### ① 標高データの読み出し（`tile/`）

**同梱（既定・全国 z10）** — `data/dem/{z}/{x}/{y}.bin`。自前形式（int16・4m 量子化・行差分・zlib）。無効値は `-32768`。

**オンライン上乗せ（任意・z11 で 0〜30km を差し替え）**:

```
https://cyberjapandata.gsi.go.jp/xyz/dem/{z}/{x}/{y}.txt      （テキスト）
https://cyberjapandata.gsi.go.jp/xyz/dem_png/{z}/{x}/{y}.png  （PNG）
```

PNG の復号（**仕様どおりに実装する。符号付き24bit**）:

```
x = 2^16·R + 2^8·G + B
x < 2^23  →  h = x × 0.01
x = 2^23  →  h = 無効値
x > 2^23  →  h = (x - 2^24) × 0.01
```

無効値は txt では `e`、PNG では `(R,G,B)=(128,0,0)`。タイルは 256×256。取得済み z11 はディスクにキャッシュする。

**#5 の帰結として、圏外でもアプリは常に動く。** 通信は「近距離を細かくする」ためだけに使う。当初あった「圏外なら観測に入らせない」という規則は不要になった。

### ② 地平線プロファイル（`terrain/Raycaster.kt`）

全方位 7,200 本（0.05°刻み）のレイを飛ばし、各方位の**最大仰角**を求める。

地球の丸みと大気差を含めた見かけの落ち込み（屈折係数 k=0.13）:

```
drop(d) = 0.87 × d² / (2 × 6,371,000)
alt(d, h) = atan( (h − h_obs − drop(d)) / d )
```

この式が **#8 の 150km 上限の根拠**でもある:

| 距離 | 落ち込み | 見える最低標高 |
|---|---|---|
| 50 km | 171 m | — |
| 100 km | 683 m | 683 m |
| 150 km | 1,537 m | 1,537 m |
| 200 km | 2,732 m | **ほぼ何も残らない** |

サンプル間隔は近距離100m・遠距離500m。1レイ約600サンプル、計約430万サンプル。**位置が確定したときに1回だけ**計算し、以後は首の動きで再計算しない。

**再計算の閾値 = 50m 移動**。根拠: 50km 先の山が画面1画素（0.066°）動く移動距離は `50000 × tan(0.066°) ≈ 57m`。GPS の測位誤差ともおおむね釣り合う。

### ③ 山の可視判定（`terrain/PeakVisibility.kt`）

**地平線プロファイルだけでは足りない。** 手前の低い尾根の上に、その裏の高い山より低く見えている山があり得るため、最大仰角の一致判定では取りこぼす。

山ごとに個別のレイマーチを行う。150km 圏内の1003山は概ね100〜200座なので、200 × 600 = 12万サンプルで済む（プロファイル計算の 1/36）。

### ④ 描画（`glass/RidgeRenderer.kt`）

| 要素 | 描き方 | 階調 |
|---|---|---|
| スカイライン | 太いストローク（3–5px） | **7（255）** |
| 尾根線 | 中太ストローク | 5 |
| 山名 | **テキスト枠**（画像の手前） | — |
| 方位（N/E/S/W） | ポリラインで自前描画（枠を節約） | 4 |
| 案内矢印 | 別画像 id 1 | **7（255）のみ** |

地平線の円（星しるべの `horizon`）は**削除**。稜線がその役目を引き継ぐ。

## 方位合わせ（#7）— 最大の技術リスク

星しるべの精度予算表:

| 用途 | 要求精度 |
|---|---|
| 解説する対象を決める | ±20° |
| ラベルを方向に置く | ±5〜10° |
| **図を実景に重ねる** | **±2〜3°** |

星しるべは**天体アライメントを実装し JVM テストまで通した後、2026-08-21 に意図的に削除**した（`docs/team-e/14_alignment-accuracy.md`、理由=「精度より UX」）。解説だけなら ±20° で足りると判断したため。

**稜線オーバーレイは本質的に一番下の行に居る。彼らが要らないと判断して捨てた精度が、こちらでは必須。**

加えて **`ObservationDefaults.STAR_MAP_FOV_DEG = 35.0` は未実測の仮値**で、プロジェクト自身が「開いている最大の不明点」に挙げている。

### 解決策: 稜線そのものを較正ターゲットにする

星ではできない。星は点で、どれがどれか分からないため。**山の稜線は形が一意なので「描いた線を実物に重ねてください」が成立する。**

2段構え:

1. **スマホ同期**（`ui/CalibrationScreen.kt`・実装済み・実機確認済み）で ±10° まで
2. **稜線合わせ**（`alignment/RidgeAlignment.kt`・新規）で ±1° まで追い込む

**副産物として画角が実測できる。** 既知方位の2点が画面上で何画素離れるかから逆算できるので、未実測の最大の穴が較正のついでに埋まる。

既存の作法を踏襲する: **確定はボタンではなく静止で取る**（「押す動作そのものが精度を壊す」）。

|---|---|---|
| **観測地** | 稜線の計算に使う緯度経度と標高。**星と違い、50m 動けば作り直しが要る** | `Locator` |
| **見通し計算** | 観測地から全方位へ地形をたどり、各方位でいちばん高く見える点を求めること | `terrain/Raycaster.kt` |
| **地平線** | 見通し計算の結果。方位ごとの仰角と、そこに立っている山 | `HorizonProfile` |
| **稜線** | 地平線をグラスに描いた線。**空と大地の境界そのもの**で、名前の無い丘も含む | `RidgeRenderer` |
| **尾根線** | 名前のある峰どうしを繋いだ線。連峰を示す。稜線とは別物 | `data/ranges.json` |
| **隠れる** | 手前の地形に遮られて見えないこと。**隠れた山は描かない** | `PeakVisibility` |
| **同梱地形** | 端末が持っている全国の標高。**これだけで動く**（画素124m） | `data/dem/` |
| **上乗せ地形** | 電波があるとき近距離だけ差し替える細かい標高（画素62m）。**通信するのはここだけ** | `tile/GsiTileClient.kt` |
| **焼き直し** | 観測地が変わって地平線を作り直すこと。**50m 動いたら** | `RidgeSession` |
| **方位合わせ** | スマホ同期で粗く、稜線を重ねて追い込む2段の較正 | `CalibrationScreen` / `RidgeAlignment` |

### ADR

`docs/adr/0001-bundled-dem-with-online-refinement.md` を書く。

星しるべの原則「外部 API に依存せず、オフラインで完結する」を**守りきる方法を選んだ**が、その判断過程は自明ではない。①18MB を APK と git に載せるのは不可逆に近い ②「なぜ全国を同梱したのか」「なぜ z10 なのか」は文脈なしでは驚く ③固定展望地方式・全部オンライン・z9/z11 という現実の選択肢を測った上で選んだ。

記録すべき骨子: 山の見え方は場所で激変する（50km先の山は1km移動で1.1°＝画面17画素ずれる）ので固定展望地方式は破綻する／海タイルは404で存在せず全国 z10 が実測 18MB に収まった／z9 の 247m は 10km 先で 21 画素となり厳密オクルージョンの判定を外すため採らなかった／オンラインは近距離の上乗せに限定し、無くても全機能が動く。

```bash
cd samples/kmp && ./gradlew :app:installDebug
```

段階5以降、鯖江または福井市内から実機で確認する。**実機でしか分からないこと**が多いので、`AGENTS.md` の「**確かめていないことを「動く」と書かない**」を厳守する。

## リスクと未確定

| リスク | 状況 |
|---|---|
| **画角35°が未実測** | プロジェクト自身が「最大の不明点」に挙げている。段階7の較正で実測して埋める |
| **±2〜3°の精度が要る** | 星しるべが「精度よりUX」で捨てた精度。稜線合わせで取りに行くが、**実機で成立するかは未検証** |
| **屋外での視認性** | 緑8階調・黒透明で太い線が昼間に見えるか。実測データが無い（星は夜の実測しかない） |
| **見通し計算の実行時間** | 430万サンプルの所要時間が端末で未計測。遅ければサンプル間隔かレイ本数を粗くする |
| **1003山で足りるか** | 鯖江の半径150km圏に**185座（うち百名山19座）**が入ることを確認済み。遮蔽後に何座残るかは段階6で判明する |
| **git に 18MB** | クローンが重くなる。星しるべの `starlink.tle`（1.8MB）の10倍。許容範囲と判断したが、実際に運用して重ければ Git LFS を検討 |
| **ローカル `main` が10コミット遅れ** | `origin/main` にドキュメント番号体系の変更（#50）が入っている。**フォーク前に `git fetch` して最新を取ること** |
